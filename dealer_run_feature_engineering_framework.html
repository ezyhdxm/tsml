Reusable framework for irregular market data

Dealer Run Feature Engineering

Dealer run is an unusually rich but difficult market-data type: many dealers, asynchronous updates, bid/ask sides, multiple quote conventions, sparse or heterogeneous quantity fields, stale observations, and strong selection effects. This document develops a reusable feature-engineering framework around those structural properties rather than around one specific model or dataset.

1. Why dealer run deserves its own framework

Dealer run should not be treated as an ordinary rectangular panel. It is better viewed as an irregular multi-agent event stream. A row says that one dealer revealed or updated one piece of market state at one time; it does not necessarily mean that the whole market changed at that moment.

Asynchronous

Different dealers and different sides update at different times.

Sparse

Coverage varies by instrument, dealer, side, time of day, and market regime.

Stateful

A quote can remain economically relevant after its last update, but it can also become stale.

Cross-sectional

The distribution across dealers often matters more than any single quote.

Multi-dimensional

Bid/ask, price/spread/yield, quantity tiers, and firm indications can coexist.

Selective

Who chooses to quote, how often, and with what size are themselves informative.

Core principle. The useful information in dealer run is not just the quote level. It is the joint state of level, dispersion, breadth, freshness, quantity, and update behavior across dealers.

2. Represent the data correctly before engineering features

The first step is to preserve the economic meaning of each field. The safest internal representation is usually a long event table with a stable schema such as:

instrument × dealer × timestamp × side × quote_type × quantity_tier → quote_value, quantity, metadata

2.1 Keep semantically different objects separate

  • Bid and ask are different sides, not interchangeable observations.
  • Price, spread, and yield are different units. They should not be pooled into the same numerical summary unless transformed to a common economic scale.
  • Quantity tiers are often a cross-section at one time, not simply repeated observations through time.
  • Missing quantity, zero quantity, and positive displayed quantity can have different meanings and should not automatically be collapsed.

2.2 Distinguish state from event

A dealer quote update is an event. The most recent valid quote from that dealer is a state. These support different feature families:

State question

What does the dealer market look like right now?

Flow question

How has dealer behavior changed over the last few minutes or hours?

3. Point-in-time construction is non-negotiable

For a prediction made at time t, every feature must be a function only of information that was observable at or before t. This sounds simple, but dealer run creates several subtle failure modes.

3.1 Evaluate windows at the prediction timestamp

A statistic defined over (t − W, t] should be evaluated at t, not only at historical quote-update timestamps and then carried forward. Otherwise an observation that has already fallen out of the window can remain embedded in the feature until the next quote event.

3.2 Apply explicit quote-age rules

The latest quote is not automatically a valid current quote. Define an age policy per use case, for example:

active(d,t) = 1{ t − last_update(d) ≤ A }

where A can be fixed, instrument-dependent, dealer-dependent, or learned through freshness features rather than hard filtering.

3.3 Use event-time cutoffs consistently

When the dealer-run source has multiple timestamps—source time, ingestion time, vendor time, correction time—the feature pipeline needs one explicit information-availability timestamp. Backfills and corrected records require special care.

Leakage test: shifting the prediction timestamp backward by one second should never expose any observation stamped after the new cutoff.

4. The three-layer feature architecture

A clean dealer-run framework separates features into three layers. This makes the feature semantics easier to understand and prevents rolling statistics from accidentally mixing current market state with historical activity.

1. Current state

Latest active quote per dealer/side/tier, then cross-sectional market summaries.

2. Trailing flow

Quote updates, revisions, entries/exits, and changes over rolling windows.

3. Data quality

Freshness, dealer coverage, missingness, staleness, and synchronization.

Most robust dealer-run feature sets can be organized almost entirely around these three layers.

5. Quote-level and dealer-level state features

Start from the latest active state for each dealer. Build quote features at the dealer level first, then aggregate across dealers. This avoids giving extra weight to dealers that happen to update more frequently.

5.1 Dealer-level quantities

  • latest bid and ask;
  • dealer mid: (bid + ask) / 2 when both sides are valid;
  • dealer bid-ask width;
  • one-sided / two-sided indicator;
  • age of bid, ask, and latest side;
  • dealer-specific displayed quantity;
  • distance from dealer quote to market consensus or external reference;
  • number of quantity tiers currently available.

5.2 Robust aggregation is usually preferable

Dealer quotes often contain outliers and stale levels. Useful market-state aggregators include median, trimmed mean, winsorized mean, weighted median, interquartile range, and median absolute deviation. Mean and standard deviation can still be retained, but they should not be the only summaries.

6. Cross-dealer consensus and disagreement

The dealer cross-section is one of the strongest distinctive advantages of dealer-run data. A model should know not only where the market is, but also how strongly dealers agree.

6.1 Location

Feature familyExamplesInterpretation
Central levelmedian bid, median ask, median midConsensus location
Best levelsbest bid, best ask, best implied widthMost aggressive executable indication
Quantilesp10 / p25 / p75 / p90Shape of dealer distribution
Robust centertrimmed mean, weighted medianLess sensitive to outliers/stale dealers

6.2 Dispersion

  • IQR and MAD of dealer bids, asks, or mids;
  • high-low range after trimming extremes;
  • cross-dealer standard deviation;
  • dispersion normalized by current quote width;
  • dispersion relative to the instrument's own recent history.

6.3 Breadth and concentration

  • number of active dealers;
  • number of two-sided dealers;
  • share of all known dealers currently active;
  • effective dealer count from concentration weights;
  • fraction of consensus supported by fresh dealers.
Interpretation: the same median quote can mean very different things when 12 fresh dealers agree tightly versus when only 2 stale dealers remain.

7. Quantity and displayed-size features

Quantity is often the hardest dealer-run field because it is sparse, dealer-dependent, instrument-dependent, and sometimes tiered. Raw quantity should therefore be treated as only one representation of size, not the final feature.

7.1 Preserve missingness semantics

At minimum keep separate indicators for:

  • quantity observed;
  • quantity missing;
  • quantity reported as zero;
  • positive displayed quantity;
  • number of dealers with usable quantity.

7.2 Normalize quantity across dealers and instruments

A raw size of 1mm can be large for one instrument and trivial for another. Better representations include:

log_size = log(1 + quantity)
dealer_relative_size = percentile(quantity | dealer, comparable history)
instrument_relative_size = percentile(quantity | instrument, comparable history)
robust_z = (log_size − rolling_median) / rolling_MAD

When history is sparse, use hierarchical normalization: dealer × sector, dealer × rating bucket, instrument peer group, or other broader pools rather than forcing an unstable per-instrument estimate.

7.3 Separate three concepts that are often confused

Current depth

How much size is displayed by active dealer states right now?

Historical capacity

How much size have dealers shown recently, such as rolling maxima?

Quote activity

How frequently are quantity-bearing quotes being updated?

These are economically different and should not share the same feature name.

7.4 Cross-dealer size structure

  • sum / median / p75 / max of current displayed quantity;
  • dealer size concentration (HHI);
  • largest dealer share and top-k dealer share;
  • effective number of size-contributing dealers;
  • bid-vs-ask displayed-size imbalance;
  • share of dealers above an instrument-relative size threshold;
  • fraction of quote coverage with known quantity.
size_imbalance = (Q_bid − Q_ask) / (Q_bid + Q_ask + ε)

7.5 Quantity ladders and quote curves

If multiple price/size tiers are available simultaneously, treat them as a quote curve. Useful features include slope, convexity, price deterioration from small to large size, number of tiers, and size required to move the quote by a fixed amount. A curve should be estimated within one quote convention and one side.

8. Rolling dynamics and event-flow features

Trailing windows are most useful for measuring market activity and change, not for reconstructing current state.

8.1 Update intensity

  • number of quote updates over 1m / 5m / 30m / 1h;
  • number of unique dealers updating;
  • updates per active dealer;
  • bid-side versus ask-side update counts;
  • quantity-bearing update count;
  • time since most recent update.

8.2 Revision direction and breadth

  • share of dealers revising tighter / wider;
  • share moving bid or ask in the same direction;
  • median dealer revision;
  • cross-dealer revision breadth;
  • number of dealer entries and exits;
  • ratio of quote additions to quote withdrawals.

8.3 Multi-horizon change

For a state summary x(t), compare short- and long-horizon changes:

Δ_W x(t) = x(t) − x(t − W)
acceleration = Δ_short x(t) − c · Δ_long x(t)

This captures both direction and whether the dealer market is accelerating away from its recent state.

8.4 Adaptive rather than only fixed windows

Fixed clock windows are easy to interpret, but activity-normalized windows can be useful too: last 10 dealer updates, last 5 unique dealer changes, or exponentially decayed summaries. A strong framework usually contains both clock-time and event-time views.

9. Relative-value and reference features

Dealer run becomes much more informative when interpreted relative to another contemporaneous reference. The reference can be a composite quote, benchmark curve, model value, ETF/CDX proxy, peer instrument, or another independently constructed fair-value signal.

9.1 Location relative to reference

  • dealer median minus reference;
  • best bid / ask distance from reference;
  • reference percentile inside dealer cross-section;
  • robust z-score of reference relative to dealer distribution;
  • fraction of dealers above/below the reference.

9.2 Disagreement between sources

Cross-source disagreement can be predictive even when neither source is universally superior. Useful features include absolute gap, signed gap, gap normalized by dealer dispersion, and persistence of the gap across windows.

normalized_gap = (dealer_consensus − reference) / (dealer_MAD + ε)

10. Freshness, coverage, and confidence are first-class features

Dealer-run datasets have time-varying information quality. Instead of hiding that fact through imputation, expose it to the model.

Freshness

Median quote age, oldest active quote, freshest quote, age dispersion, fresh-dealer share.

Coverage

Active dealers, known-quantity dealers, bid/ask coverage, two-sided coverage.

Synchronization

Bid/ask age difference, fraction of dealers whose two sides were refreshed close together.

Reliability

Missingness rate, outlier share, stale share, duplicated updates, inconsistent tiers.

These features also make model diagnostics easier: error can be stratified by the quality of the dealer-run state available at prediction time.

12. Recommended implementation architecture

A reusable pipeline benefits from keeping raw normalization, state construction, and feature aggregation separate.

raw dealer-run events
        │
        ▼
normalize schema / units / timestamps
        │
        ├──► dealer latest-state engine
        │        └──► cross-dealer state features
        │
        ├──► rolling event-flow engine
        │        └──► update / revision / entry-exit features
        │
        ├──► quantity normalization engine
        │        └──► current depth / capacity / concentration features
        │
        └──► quality engine
                 └──► age / coverage / missingness features
                         │
                         ▼
                 point-in-time feature table

12.1 Prefer state tables over repeated full-window scans

For large datasets, repeatedly slicing every historical window for every prediction row becomes expensive. Maintain per-dealer latest state and incremental rolling statistics where possible. Vectorized as-of joins, indexed event arrays, deques, or a streaming state machine are usually more scalable than nested Python loops.

12.2 Name features by their economic meaning

Feature names should distinguish current_*, rolling_update_*, historical_capacity_*, coverage_*, and freshness_*. This simple naming convention prevents semantic drift later in research.

13. How to evaluate dealer-run feature families

Feature engineering should be treated as a sequence of economic hypotheses rather than an unrestricted feature dump.

13.1 Ablate by family

  1. baseline without dealer run;
  2. + current consensus level;
  3. + cross-dealer dispersion and breadth;
  4. + freshness and coverage;
  5. + quantity / depth features;
  6. + rolling update-flow features;
  7. + relative-value features;
  8. + dealer normalization / advanced quote-curve features.

13.2 Evaluate conditional performance

Average accuracy can hide where dealer run helps. Report feature-family gains by:

  • dealer coverage;
  • quote freshness;
  • instrument liquidity;
  • time of day;
  • quantity availability;
  • market volatility regime;
  • number of two-sided dealers;
  • short versus long time since last market event.

13.3 Inspect feature stability, not just importance

For each important feature, examine missingness, temporal drift, distribution by instrument/dealer, SHAP direction, monotonicity, and stability across train/test periods. A feature that is highly predictive but unstable may be less valuable than a weaker but persistent one.

14. Suggested rollout order

PriorityBuildReason

Practical rule: begin with a small, semantically clean set of state, dispersion, freshness, and normalized quantity features. Only then add more elaborate rolling statistics. The information architecture matters more than the raw feature count.

15. Bottom line

Dealer run is valuable precisely because it reveals a market as a collection of heterogeneous dealer opinions rather than as one consolidated number. The right feature-engineering abstraction is therefore:

Dealer run = current multi-dealer state + disagreement + liquidity/size + update flow + information quality

A reusable framework should preserve dealer identity long enough to construct economically meaningful dealer states, normalize heterogeneous quantity, evaluate all features point-in-time, and then summarize the dealer cross-section robustly. This makes the resulting features useful across different instruments, vendors, targets, and downstream time-series ML models.
