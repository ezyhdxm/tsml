Time Series ML Research & Iteration Framework

A versatile, model-agnostic workflow for building, diagnosing, comparing, and improving machine-learning systems on temporal and irregularly sampled data.

A living research artifact—not a pipeline for any single asset class, dataset, or prediction problem.

Core idea

Point-in-time data→Time-aware split→Baseline→Diagnostics→Features→Model comparison→Residual analysis→Robustness→Next iteration
Primary principle: every improvement should correspond to a falsifiable hypothesis about information, dynamics, or model misspecification, and should be evaluated on future/out-of-sample data.

Design principles

Point-in-time

Features must be available at prediction time. Model time, event time, and observation time may differ.

Irregular-time aware

Use actual elapsed time when sampling is irregular; event lags alone can mix very different horizons.

Paired evaluation

Compare models on the same observations and inspect the distribution of improvements, not just one aggregate score.

Residual-driven

Residual structure is a map of what the model has not learned yet.

Segment-aware

Always identify regimes/entities/horizons where aggregate improvements fail.

Iterative

Each run should produce a concrete next hypothesis rather than an open-ended list of experiments.

End-to-end pipeline

0. Problem Definition

  • Define the prediction target, prediction timestamp, forecast horizon, entity/index structure, loss function, and operational decision.
  • Write down exactly what information is available at prediction time.
  • Separate economic/event time, observation/report time, and prediction/decision time when they differ.

1. Point-in-Time Data Construction

  • Build features using only information observable at the prediction timestamp.
  • Audit joins, as-of logic, delayed labels, revisions, duplicate/tied events, and timestamp resolution.
  • Create data-quality summaries for missingness, staleness, coverage, sampling intensity, and reporting delay.

2. Time-Aware Splitting & Backtesting

  • Use chronological train/validation/test splits or walk-forward evaluation.
  • Avoid random splits when temporal dependence or regime drift matters.
  • Choose an evaluation unit and preserve it in paired comparisons.

3. Baseline Models

  • Start with simple persistence, seasonal/rolling baselines, linear models, and a strong tree-based baseline.
  • Record baseline metrics and segment-level failures before adding complexity.
  • Keep a frozen reference run for paired comparisons.

4. Exploratory Temporal Structure

  • Study target dynamics in event time and clock time separately.
  • For irregular timestamps, condition dependence on actual elapsed time rather than relying only on integer lags.
  • Inspect seasonality, structural breaks, regime shifts, cross-entity dependence, missingness, and sampling intensity.

5. Feature Engineering

  • Create lagged states, continuous-time decay/EWMA states, rolling statistics, calendar/regime features, and cross-entity aggregates.
  • Prefer causal/point-in-time transformations whose availability can be proven.
  • Add feature families incrementally so model improvements remain attributable.

6. Residual Diagnostics

  • Define residual = y_true - y_pred using out-of-sample / out-of-fold predictions.
  • Check conditional bias, event-lag dependence, elapsed-time dependence, sign persistence, magnitude persistence, and cumulative drift.
  • Use residual analysis to identify missing state, stale information, regime dependence, heteroskedasticity, and segment-specific misspecification.

7. Residual-to-Feature Loop

  • If residual structure is predictable using information available before the current prediction, convert it into candidate state features.
  • Test simple last-residual/age features before complex second-stage residual models.
  • Require strict point-in-time construction for all residual-derived features.

8. Model Comparison

  • Compare runs on the exact same observations whenever possible.
  • Report paired loss differences overall and by segment; include distributions, win rates, and confidence intervals or clustered bootstrap where appropriate.
  • Do not keep a model merely because the aggregate metric improved if a critical segment deteriorated materially.

9. Interpretation & Failure Analysis

  • Use feature importance, SHAP/permutation diagnostics, calibration curves, and targeted slices.
  • Focus on actionable failures: where, when, and under what information state the model misses.
  • Distinguish stable structural effects from artifacts caused by preprocessing or evaluation.

10. Robustness

  • Stress different time periods, regimes, entities, horizons, missing-data states, and data-source variants.
  • Check sensitivity to lookback windows, decay parameters, outlier rules, and timestamp definitions.
  • Repeat key conclusions on later unseen periods.

11. Production & Monitoring

  • Version data, features, model, and evaluation artifacts.
  • Monitor target drift, feature drift, residual drift, latency/availability, missingness, and segment-level error.
  • Keep research diagnostics compatible with online information constraints.

12. Iteration Log

  • For every run, store hypothesis, code/data version, feature changes, metrics, plots, interpretation, and next action.
  • Maintain one living HTML report as the research source of truth.
  • Use the report as the handoff artifact between notebooks, collaborators, and future AI-assisted sessions.

Residual analysis for temporal ML

Let an out-of-sample residual be e_i = y_i - ŷ_i. Residual diagnostics should answer four questions:

QuestionDiagnosticTypical implication
Is the model systematically biased?Mean/median residual, sign rate, conditional residual slicesCalibration or missing nonlinear effect
Is there temporal memory?Event-lag dependence + correlation versus actual elapsed timeMissing dynamic state / stale information
Does difficulty cluster?|residual|, robust scale, tail loss versus elapsed time/regimeHeteroskedasticity / uncertainty state
Does performance drift?Time-bucket summaries, rolling bias, CUSUM-style diagnosticsRegime change / feature drift
For irregular timestamps, a standard integer-lag ACF can be misleading because “lag 1” may mean seconds for one entity and days for another. Pair event-lag diagnostics with elapsed-time-conditioned diagnostics.

Point-in-time residual state

If historical residuals become observable at available_time_j and the current prediction is made at prediction_time_i, only observations satisfying

available_time_j < prediction_time_i

may enter a residual-derived feature. A generic continuous-time state is:

S_i(τ) =
Σ_j exp(-(prediction_time_i - available_time_j)/τ) · residual_j
----------------------------------------------------------------
Σ_j exp(-(prediction_time_i - available_time_j)/τ)

Useful variants include entity-level state, group-ex-current-entity state, market/global state, and robust absolute-residual state.

Recommended experiment ladder

  1. Baseline: freeze the current reference model and exact evaluation sample.
  2. Diagnose: identify one specific residual or segment pattern.
  3. Simple feature: add the smallest feature that should remove that pattern.
  4. Paired OOS test: compare against baseline on the same future observations.
  5. Residual re-check: verify that the targeted residual structure actually weakened.
  6. Robustness: repeat over later windows and important segments.
  7. Keep or revert: retain the change only if the gain is stable and interpretable.

Handoff protocol

This repository should function as the project’s source of truth. A future session can start by reading the latest framework and experiment log, then continue from the latest unresolved hypothesis.

run experiment
→ summarize metrics/plots
→ update framework + experiment log
→ commit to GitHub
→ next session reads latest GitHub state
→ propose / implement next experiment

Scope

This framework is intentionally broad. It is suitable for forecasting, event-driven prediction, temporal panel data, irregularly sampled observations, market/microstructure data, demand or operational forecasting, sensors, and other sequential ML tasks.

Domain-specific rules should live in separate experiment notes or modules so the core framework remains reusable.
