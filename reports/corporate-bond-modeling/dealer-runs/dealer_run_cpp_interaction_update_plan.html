Dealer Run + CP+ Feature Upgrade Plan

Column-aware design using the concrete CP+ fields now visible in the merged observation table. The main goal is to turn CP+ from “one more baseline column” into a disciplined point-in-time reference layer: self-quality checks, rates/credit decomposition, dealer-vs-CP+ residual features, historical calibration, and leakage-safe dynamics.

1. CP+ columns currently available

The visible merged table contains the following CP+ fields:

ColumnRoleRecommendation
BID_YIELD_CPP, ASK_YIELD_CPPCP+ yield-side quoteUse as reference context / yield-space features, but never subtract directly from dealer spread.
BID_SPREAD_CPP_EXEC_TIME, ASK_SPREAD_CPP_EXEC_TIME, MID_SPREAD_CPP_EXEC_TIMECP+ spread observed/aligned at execution timePrimary CP+ spread reference candidate for dealer-spread interaction, subject to timestamp audit.
LASTUPDATETIME_CPPCP+ update timestampCritical for age, staleness, and point-in-time eligibility.
BID_SPREAD_CPP, ASK_SPREAD_CPP, MID_SPREAD_CPPAnother CP+ spread view/stateAudit against EXEC_TIME fields before modeling. If these are post-execution/latest values, they may leak.
D_CPP_BM_SPREAD, D_CPP_BM_SPREAD_ASK, D_CPP_BM_SPREAD_BIDDerived CP+/benchmark quantitiesDo not use until exact semantic definition and availability timing are confirmed.
CPP_SIDED_ERROR, CPP_MID_ERRORCP+ error/residual fieldsCurrent-row values are leakage candidates if they use the realized trade. Quarantine from model inputs; use only lagged historical versions after strict point-in-time construction.
Primary modeling reference: for dealer-spread interactions, start from BID_SPREAD_CPP_EXEC_TIME / ASK_SPREAD_CPP_EXEC_TIME. Keep the non-EXEC_TIME spread fields in an audit/debug layer until their temporal semantics are proven.

2. First required audit: EXEC_TIME vs non-EXEC_TIME CP+ fields

The sample rows appear to show the EXEC_TIME spread fields equal to BID/ASK/MID_SPREAD_CPP, but this must be measured over the full dataset.

Audit equality and divergence
pairs = [
    ("BID_SPREAD_CPP_EXEC_TIME", "BID_SPREAD_CPP"),
    ("ASK_SPREAD_CPP_EXEC_TIME", "ASK_SPREAD_CPP"),
    ("MID_SPREAD_CPP_EXEC_TIME", "MID_SPREAD_CPP"),
]

audit = {}
for a, b in pairs:
    valid = data[[a, b]].dropna()
    diff = valid[a] - valid[b]
    audit[f"{a}_vs_{b}"] = {
        "n": len(valid),
        "equal_rate": np.isclose(valid[a], valid[b], rtol=0, atol=1e-12).mean(),
        "mean_abs_diff": diff.abs().mean(),
        "p99_abs_diff": diff.abs().quantile(0.99),
        "max_abs_diff": diff.abs().max(),
    }

Interpretation:

  • If equality is essentially 100%, keep one set only to avoid duplicated features.
  • If they differ, determine whether the non-EXEC_TIME columns are a later/latest CP+ state. If yes, they are debug-only for execution-time prediction.
  • If they represent distinct but point-in-time-valid concepts, name the distinction explicitly and feature them separately.

3. CP+ self-quality features from the columns you already have

Before asking whether dealer quotes disagree with CP+, quantify whether CP+ itself is internally coherent.

Reference self-quality features
df["cpp_spread_width_exec"] = (
    df["BID_SPREAD_CPP_EXEC_TIME"]
    - df["ASK_SPREAD_CPP_EXEC_TIME"]
)

df["cpp_spread_mid_reconstructed"] = 0.5 * (
    df["BID_SPREAD_CPP_EXEC_TIME"]
    + df["ASK_SPREAD_CPP_EXEC_TIME"]
)

df["cpp_spread_mid_consistency_error"] = (
    df["MID_SPREAD_CPP_EXEC_TIME"]
    - df["cpp_spread_mid_reconstructed"]
)

df["cpp_yield_width"] = (
    df["BID_YIELD_CPP"] - df["ASK_YIELD_CPP"]
)

df["cpp_width_crossed"] = df["cpp_spread_width_exec"].lt(0)
df["cpp_width_zero"] = df["cpp_spread_width_exec"].eq(0)
df["cpp_two_sided"] = (
    df["BID_SPREAD_CPP_EXEC_TIME"].notna()
    & df["ASK_SPREAD_CPP_EXEC_TIME"].notna()
)

In the visible sample, bid spread is above ask spread, so the natural spread-width convention is bid - ask. These self-quality features should be retained even if CP+ remains the baseline.

4. A useful new decomposition: infer the benchmark yield from CP+ yield and spread

The current columns contain both CP+ yield and CP+ spread. That lets us recover the benchmark component implied by CP+:

benchmark_yield ≈ yield - spread.

In the visible sample, the bid- and ask-implied benchmark yields appear to line up very closely, which makes this an excellent consistency check and a potentially useful rates-context feature.

Implied benchmark-yield features
df["cpp_implied_bm_yield_bid"] = (
    df["BID_YIELD_CPP"] - df["BID_SPREAD_CPP_EXEC_TIME"]
)

df["cpp_implied_bm_yield_ask"] = (
    df["ASK_YIELD_CPP"] - df["ASK_SPREAD_CPP_EXEC_TIME"]
)

df["cpp_implied_bm_yield_mid"] = 0.5 * (
    df["cpp_implied_bm_yield_bid"]
    + df["cpp_implied_bm_yield_ask"]
)

df["cpp_implied_bm_side_disagreement"] = (
    df["cpp_implied_bm_yield_bid"]
    - df["cpp_implied_bm_yield_ask"]
)

df["cpp_yield_width_minus_spread_width"] = (
    df["cpp_yield_width"] - df["cpp_spread_width_exec"]
)

This separates CP+ into:

  • rates/benchmark component: implied benchmark yield;
  • credit component: CP+ spread;
  • liquidity/uncertainty component: CP+ bid-ask width and age.
Do not compare yield and spread directly. The benchmark decomposition is valid only after confirming units (e.g. percentage points vs bps) are consistent.

5. CP+ timestamp and staleness features

LASTUPDATETIME_CPP should be a first-class feature, not merely a filter.

Reference age and validity
cpp_ts = pd.to_datetime(
    df["LASTUPDATETIME_CPP"],
    utc=True,
    errors="coerce",
)

obs_ts = pd.to_datetime(
    df["EFFECTIVE_DATETIME_TS"],
    utc=True,
    errors="coerce",
)

df["cpp_age_seconds"] = (obs_ts - cpp_ts).dt.total_seconds()

df["cpp_timestamp_missing"] = cpp_ts.isna()
df["cpp_timestamp_future"] = cpp_ts.gt(obs_ts)
df["cpp_age_negative"] = df["cpp_age_seconds"].lt(0)

for seconds in (60, 300, 900, 3600):
    df[f"cpp_fresh_le_{seconds}s"] = (
        df["cpp_age_seconds"].ge(0)
        & df["cpp_age_seconds"].le(seconds)
    )

For the actual feature builder, compare CP+ time against the same information_cutoff used for dealer state, not necessarily raw trade time.

7. Explicit metric contract: spread vs yield

The new columns make a previously ambiguous issue concrete: CP+ has both yield and spread. The interaction helper should reject metric mismatch.

Recommended metric guard
def _validate_reference_metric(
    dealer_metric: str,
    reference_metric: str,
) -> None:
    if dealer_metric != reference_metric:
        raise ValueError(
            "Dealer quote and CP+ reference must be in the same metric "
            f"before interaction features are computed: "
            f"{dealer_metric=} {reference_metric=}"
        )

Recommended policy:

  • Dealer spread ↔ *_SPREAD_CPP_EXEC_TIME.
  • Dealer yield ↔ BID_YIELD_CPP / ASK_YIELD_CPP.
  • Dealer price ↔ a point-in-time CP+ price only if one exists or after a validated conversion.

8. Requested-size interactions

If requested RFQ size is available at prediction time, interpolate the dealer ladder at the requested size and compare directly with CP+.

Keep the provenance fields introduced in the new code:

  • is_exact;
  • is_interpolated;
  • is_extrapolated (add this explicitly if extrapolation remains allowed);
  • lower_qty, upper_qty;
  • log_bracket_span;
  • size-specific age_seconds.

Recommended requested-size features:

  • requested_size_dealer_coverage;
  • requested_size_exact_share;
  • requested_size_interpolated_share;
  • requested_size_cross_share;
  • requested_size_exact_cross_share;
  • requested_size_cross_edge_median;
  • requested_size_consensus_aggressive_edge;
  • requested_size_fresh_weighted_cross_share.

9. Use CP+ error columns only historically — never current-row

CPP_SIDED_ERROR and CPP_MID_ERROR are potentially very valuable, but also the highest leakage risk in the table.

Default rule: do not put the current row's CPP_SIDED_ERROR or CPP_MID_ERROR into the model until it is proven they are known before the prediction event. If they use realized trade information, they are labels/residuals.

The safe and potentially powerful use is lagged CP+ calibration from strictly prior trades.

Lagged historical CP+ calibration
df = df.sort_values(["CUSIP", "EFFECTIVE_DATETIME_TS"])

g = df.groupby("CUSIP", sort=False)

df["cpp_mid_error_lag1"] = g["CPP_MID_ERROR"].shift(1)
df["cpp_sided_error_lag1"] = g["CPP_SIDED_ERROR"].shift(1)

# Simple expanding prior-only bias estimates.
df["cpp_mid_error_prior_mean"] = g["CPP_MID_ERROR"].transform(
    lambda s: s.shift(1).expanding(min_periods=3).mean()
)

df["cpp_mid_abs_error_prior_mean"] = g["CPP_MID_ERROR"].transform(
    lambda s: s.abs().shift(1).expanding(min_periods=3).mean()
)

df["cpp_sided_error_prior_mean"] = g["CPP_SIDED_ERROR"].transform(
    lambda s: s.shift(1).expanding(min_periods=3).mean()
)

More useful production versions would use time-decay / rolling time windows and hierarchical fallback:

CUSIP → issuer → sector → global, always based on strictly prior observations.

This is a natural residual-modeling framework: dealer-run signals should explain when CP+ is wrong, while prior CP+ errors estimate whether it has been systematically wrong in the same direction.

11. D_CPP_BM_SPREAD* columns: treat as quarantined until semantics are verified

The fields D_CPP_BM_SPREAD, D_CPP_BM_SPREAD_ASK, and D_CPP_BM_SPREAD_BID look economically promising, but their names alone are not sufficient to determine whether they are:

  • CP+ minus benchmark spread;
  • a benchmark-move adjustment;
  • a post-event delta;
  • or another derived diagnostic.

Before modeling them, document:

  1. exact formula;
  2. source timestamps used;
  3. whether any realized trade/target enters the calculation;
  4. whether they are available before information_cutoff.

If they are genuinely point-in-time benchmark-relative deltas, then good features would include:

  • d_cpp_bm_mid, d_cpp_bm_bid, d_cpp_bm_ask;
  • d_cpp_bm_bid_minus_ask;
  • d_cpp_bm_mid_minus_side_avg;
  • interaction with dealer-consensus residual;
  • interaction with implied benchmark-yield movement.

12. CP+ age × dealer age interactions

Now that CP+ has its own timestamp, explicitly compare information freshness across sources.

Relative freshness
record["dealer_minus_cpp_age_seconds"] = (
    dealer_age_median_seconds - cpp_age_seconds
)

record["fresh_dealer_vs_stale_cpp"] = (
    dealer_age_median_seconds <= 60
    and cpp_age_seconds > 300
)

record["stale_dealer_vs_fresh_cpp"] = (
    dealer_age_median_seconds > 300
    and cpp_age_seconds <= 60
)

A large dealer-vs-CP+ disagreement is much more interesting when the dealer state is fresh and CP+ is stale than in the opposite configuration.

13. CP+ reference-width normalization needs a floor

Normalizing crossing by CP+ width is useful, but a tiny positive width can explode the ratio.

Usable-width guard
ref_width = ref_bid_spread - ref_ask_spread

ref_width_usable = (
    pd.notna(ref_width)
    and ref_width > min_reference_width
)

normalized_cross = (
    cross_edge / ref_width
    if cross_edge > 0 and ref_width_usable
    else np.nan
)

Calibrate min_reference_width from the empirical CP+ quote resolution/distribution; do not choose it arbitrarily.

15. Builder changes

The public observation builder should expose the concrete CP+ columns explicitly instead of passing an ambiguous generic reference pair.

Recommended builder arguments
reference_bid_spread_col: str = "BID_SPREAD_CPP_EXEC_TIME"
reference_ask_spread_col: str = "ASK_SPREAD_CPP_EXEC_TIME"
reference_mid_spread_col: str = "MID_SPREAD_CPP_EXEC_TIME"

reference_bid_yield_col: str = "BID_YIELD_CPP"
reference_ask_yield_col: str = "ASK_YIELD_CPP"

cpp_mid_error_col: str | None = "CPP_MID_ERROR"
cpp_sided_error_col: str | None = "CPP_SIDED_ERROR"

requested_size_col: str | None = None

Then construct a small CP+ state object/record once per observation and pass it to the reference interaction helper.

CP+ state at observation time
cpp_state = {

17. Recommended ablation sequence

  1. CP+ spread baseline only.
  2. + CP+ self-quality (width, age, two-sided, mid consistency).
  3. + implied benchmark/rates component.
  4. + existing dealer current-state features.
  5. + common-size dealer–CP+ consensus edge.
  6. + same-side-better breadth.
  7. + opposite-side crossing breadth/penetration.
  8. + requested-size features.
  9. + dealer/CP+ relative freshness.
  10. + lagged historical CP+ error calibration.
  11. + signed quote revision flow.
  12. + dealer–CP+ residual dynamics.
Main hypothesis: these columns make CP+ useful not only as a baseline level, but as a decomposable reference state. The strongest dealer-run alpha should come from fresh, size-supported, cross-dealer disagreement with CP+ after controlling for CP+ age, width, benchmark movement, and its own recent calibration error.

Implementation note: CPP_SIDED_ERROR, CPP_MID_ERROR, and D_CPP_BM_SPREAD* remain quarantined from current-row model features until their formulas and information timing are verified.
